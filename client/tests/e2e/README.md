# End-to-end tests: the client against a real server

The unit suites in `../` cover each piece: the session state machine, the
error taxonomy, the list model's roles, the player's throttle. None of them
touch a server. This directory does, because the failures that survive all of
them are the ones at the seam — a resume offset that never leaves the client, a
Range header the server ignores, a profile header that arrives on the wrong
paths.

## Running it

```sh
cd client
cmake -S . -B build-test -DSTREAM_BUILD_TESTS=ON -G Ninja
cmake --build build-test -j 8
ctest --test-dir build-test -R e2e --output-on-failure
```

`harness.py` is usable on its own too, which is useful when you want a server to
point a client at by hand:

```sh
python3 client/tests/e2e/harness.py up   --dir "$TMPDIR/stream-e2e"
python3 client/tests/e2e/harness.py down --dir "$TMPDIR/stream-e2e"
```

`up` prints one JSON line and writes it to `<dir>/fixture.json`. `down` stops the
server and deletes the directory.

## What the fixture is, and why

A real server. A real `server.toml`, a real SQLite database with its own signing
key, a real account, and a library root holding a real clip generated by
`ffmpeg` — `testsrc` and a sine tone, encoded to H.264 and AAC in a Matroska
container.

Random bytes would be simpler and would only exercise the error paths. The
player needs a container the backend can probe and the decoder can open, or
"playback works" is an untested claim.

Two settings differ from a deployment, both deliberately:

- **`scrypt_n = 1024`** rather than 2^15. ~1 ms instead of ~100 ms. The tests
  sign in repeatedly and are not about scrypt; the backend's own suite asserts
  the production parameters.
- **`allow_insecure_transport` is *not* set.** The server binds loopback and
  permits plain HTTP there on its own. Setting the flag would grant an
  exception the deployment does not need, and the client would then be tested
  against a configuration nobody should ship.

## Two things this machine needed

`python -m streamserver` does not work. The package has no `__main__`; its
entry point is the console script `streamserver = streamserver.cli:main`, so the
harness runs that module.

`http_proxy` is set in the environment here, so anything reaching loopback has
to say `no_proxy` or it is sent to the proxy. The harness sets it for every
process it starts. Without it the server starts, answers its own health check,
and is then unreachable from everything else including the tests.

## When the fixture fails to start

It says why. If the server process exits during startup the harness reads its
log and puts the output in the error, because a fixture that fails with
"connection refused" and no explanation is the least useful thing in a suite.
